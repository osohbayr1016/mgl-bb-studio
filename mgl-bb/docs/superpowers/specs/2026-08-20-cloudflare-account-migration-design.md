## 2. Батлагдсан шийдвэрүүд

1. **Хамрах хүрээ:** Cloudflare-ийн бүх нөөц. GitHub хөндөхгүй.
2. **Домэйн:** одоо хийхгүй. Шинэ `workers.dev` / `pages.dev` хаяг авна.
3. **Нууцууд:** хуучныг сэргээх боломжгүй нь батлагдсан → шинээр үүсгэнэ.
4. **Зогсолт:** D1-ийн хувьд 20–40 минутын цонх зайлшгүй. Шөнө/амралтын
   өдөр хийж, хэрэглэгчид мэдрэгдэхгүй болгоно.
5. **Төлбөр:** Workers Paid ($5/сар) төлөгдсөн гэж хэрэглэгч мэдэгдсэн.
   Гүйцэтгэлийн 0-р алхамд *аль акаунт дээр* төлөгдсөнийг батална.

## 4. Хязгаарлалтууд ба тэдгээрийн үндэслэл

Эдгээр нь дизайны сонголт биш, платформын хатуу хязгаар. Тус бүрийг шалгаж
баталсан.

### 4.1 URL хэвээр үлдэх боломжгүй

`mgl-progress-api.**anandoctane4**.workers.dev` дэх `anandoctane4` бол
**акаунтын** workers.dev дэд домэйн. Cloudflare-т акаунт бүр дэлхий даяар
давтагдашгүй ганц дэд домэйнтэй бөгөөд хуучин акаунт түүнийг эзэмшсээр,
тэр доор нь өөр 11 төсөл ажиллаж байна.

`mgl-progress-frontend.pages.dev` мөн адил дэлхий даяар давтагдашгүй нэр —
шинэ акаунт дээр дахин авах боломжгүй.

**Дүгнэлт:** хоёр URL хоёулаа солигдоно. Үүнийг үүрд шийдэх ганц зам бол
өөрийн домэйн, гэвч тэр нь зориудаар хойшлогдсон.

### 4.2 Нууцыг «шилжүүлэх» боломжгүй

Cloudflare нь secret-ийг зөвхөн бичдэг, буцааж уншуулдаггүй — dashboard дээр ч,
API-аар ч, `wrangler`-ээр ч. `wrangler secret list` зөвхөн **нэрийг** буцаана.

`backend/.dev.vars` доторх `JWT_SECRET` нь production-ынхтай **ижил биш** нь
шалгагдсан: тэр утгаар гарын үсэг зурсан token production-д
`401 {"error":"Invalid or expired token"}` буцаасан.

### 4.3 D1-д «зогсолтгүй» шилжилт байхгүй

Cloudflare нь хоёр D1 санг зэрэг синк хийх, эсвэл репликлэх механизм өгдөггүй.
Дараалал зайлшгүй: бичилт зогсоох → `d1 export` → `d1 execute --file` →
тулгах → шилжүүлэх.

### 4.4 Шинэ D1-ыг migration-аар босгох боломжгүй

Production-д **178** migration бүртгэгдсэн атлаа репод ~147 файл байна. Мөн
дөрвөн файл 1 байт хоосон (`0021`, `0022`, `0024`, `0025`), `0023` тэдгээрээс
хамаардаг тул `migrations apply` шинэ санг босгож чадахгүй. `project_threads`
болон `project_thread_messages` хүснэгтүүд ямар ч migration файлд байхгүй,
зөвхөн production-д оршдог.

**Дүгнэлт:** шинэ D1-ыг зөвхөн `d1 export`-оос сэргээнэ.

### 4.5 Container Worker-ийн эх код репод байхгүй

`mgl-stirling` ба `mgl-weasyprint` хоёр production дээр ажиллаж байгаа боловч
эх кодыг нь `5f1538f` commit устгасан. `5f1538f~1`-ээс сэргээнэ. Хоёул
`[[containers]]` + Durable Object бүхий Cloudflare Containers Worker тул
байрлуулахад **Docker** шаардлагатай.

`mgl-weasyprint` нь `lib/clientReport.ts`-ийн клиент PDF тайлангийн амьд
хамаарал — заавал сэргээнэ.

## 6. Шилжилтийн дараалал

### Алхам 0 — Урьдчилсан нөхцөл батлах

1. `info@mglenc.com` акаунт дээр **Workers Paid** идэвхтэй эсэхийг батлах.
   **Browser Rendering** (бүх PDF үүсгэлт) ба **Containers** (`mgl-stirling`,
   `mgl-weasyprint`) хоёр үүнийг шаарддаг. SQLite-д тулгуурласан Durable
   Object нь үнэгүй төлөвлөгөөнд ч боломжтой тул `MglMcpAgent` дангаараа
   төлбөрийн шалтгаан болохгүй — гэхдээ дээрх хоёрын улмаас Paid хэрэгтэй.
2. Локал Docker ажиллаж байгаа эсэх.
3. Тухайн акаунт дээр **R2 идэвхжүүлэх**.
4. Хуучин акаунтын D1-ийн бүрэн `export`-ыг **нөөц** болгон авах
   (шилжилт бүтэхгүй байсан ч гэсэн энэ файл гарт байх ёстой).

### Алхам 1 — Шинэ орчин босгох (production хөндөхгүй)

Компанийн акаунт дээр D1, KV, хоёр R2 сав (APAC) үүсгэх. Гарсан ID-уудыг
тэмдэглэх. Container Worker хоёрын эх кодыг `5f1538f~1`-ээс сэргээж,
`account_id`-г солиод байрлуулах.

### Алхам 2 — R2-ийн урьдчилсан хуулбар (зогсолтгүй)

8.27 ГБ-ыг **R2 Super Slurper**-ээр хуулна: эх савыг S3-тэй нийцтэй эх
сурвалж болгон бүртгээд, Cloudflare сервер талдаа шууд хуулна — хэрэглэгчийн
интернэтээр дамжихгүй. Үүнд эх акаунтад R2 API token (Access Key ID + Secret)
хэрэгтэй.

Энэ алхмыг **шилжилтээс хэдэн өдрийн өмнө** гүйцэтгэнэ. Шилжилтийн шөнө зөвхөн
хооронд нэмэгдсэн зөрүүг нөхнө.

**Нөөц зам:** Super Slurper-ийн R2→R2 хувилбар саадтай тохиолдолд `rclone`-оор
хоёр R2 савыг S3 remote болгон бүртгээд `rclone sync` хийнэ. Энэ тохиолдолд
8.27 ГБ хэрэглэгчийн интернэтээр дамжих тул хугацаа мэдэгдэхүйц уртсана —
тиймээс Super Slurper эхний сонголт хэвээр.

### Алхам 3 — Нууцууд ба кодын өөрчлөлт

Нууцуудыг эх сурвалжаас нь дахин авч шинэ Worker-т тавих (§7).
Кодын өөрчлөлтийг нэг PR болгон бэлтгэх (§8), гэхдээ **хараахан байрлуулахгүй**.

### Алхам 4 — Гадаад үйлчилгээнд шинэ URL нэмэх

Google OAuth redirect URI, Speechmatics webhook URL-д **шинийг нэмнэ, хуучныг
устгахгүй**. Хоёулаа зэрэг ажиллаж байвал буцах зам нээлттэй үлдэнэ.

### Алхам 5 — Өгөгдлийн шилжилт (шөнийн цонх, 20–40 мин)

1. Ажилтнуудад урьдчилан мэдэгдэх.
2. Хуучин Worker-ийг бичилт хүлээхгүй болгох (эсвэл хэрэглэгчдийг гаргах).
3. `d1 export --remote` → бүрэн SQL файл.
4. Шинэ D1 руу `d1 execute --remote --file`.
5. R2-ийн зөрүүг нөхөх.
6. Суурь тоонуудыг тулгах: 109 / 73 / 25 / 8985 / 178.

### Алхам 6 — Шилжүүлэх

Шинэ Worker-ийг байрлуулах → frontend-ийг шинэ API хаягтайгаар барьж Pages руу
байрлуулах → гараар шалгах (§9).

### Алхам 7 — Ажиглалт ба цэвэрлэгээ

- Хуучин акаунтыг **2–4 долоо хоног** уншихад бэлэн хэвээр үлдээнэ.
- `.claude/settings.local.json`-д commit хийгдсэн Cloudflare API token-ыг
  **цуцлах** (хуучин акаунтынх, `74ce74e`-ээс хойш түүхэнд байгаа).
- Хугацаа өнгөрсний дараа хуучин нөөцүүдийг устгах.
