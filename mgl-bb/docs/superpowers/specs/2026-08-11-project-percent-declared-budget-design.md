# Төслийн прогрессийн хувийг зарласан төсвөөр бодох

**Огноо:** 2026-08-11
**Төлөв:** хэрэгжсэн (deploy хүлээгдэж байгаа — §7-ийн шалгах query эхэлнэ)

## 1. Асуудал

Системд төслийн прогрессийн хувийг бодох **хоёр өөр** томьёо зэрэг оршиж, тэдгээр нь
өөр хоорондоо зөрдөг:

| | Хаана | Математик |
|---|---|---|
| **Харагдац** | `PROJECT_LIST_SQL` (`backend/src/routes/projects.ts:95`) | Түвшин бүрт **бодит** хүүхдийн жингийн нийлбэрээр нормчилно: `SUM(w × pct) / NULLIF(SUM(w), 0)` |
| **Оноо** | `calcProjectProgress` (`backend/src/routes/progress.ts:1137`) | **Зарласан** төсвөөр хуваана: `… × 100.0 / d.weight_percent`, түвшин бүрт `/ 100.0`, эцэст нь `× share/100` |

Хоёр томьёо зөвхөн жин бүх түвшинд яг 100 болж нийлсэн үед тохирдог. Жингийн
нийлбэрийг **өгөгдлийн сан ч, API ч шалгадаггүй** (`normalizeTeamShares`,
`projects.ts:60-73` нь зөвхөн утга бүрийг 0..100 хооронд таглана).

Хамгийн мэдэгдэхүйц илрэл нь багийн хуваарь (`project_team_shares.share_percent`)
дээр гардаг: хуваарийн нийлбэр 60 байхад тэдгээр баг бүрэн дуусахад карт **100%**
харуулах ба оноо/авто-архив **60%** гэж үзнэ.

Энэ байдал санамсаргүй биш, тогтмол давтагддаг: админ баг нэмэхэд мөр
`share_percent = 0`-оор шууд хадгалагддаг (`frontend/src/features/projects/setup/useTeamShares.ts:58`).

## 2. Шийдвэр

**Дутуу хувь = хийгдээгүй ажил.** Хуваарь эсвэл жин 100 хүрээгүй байгаа нь
«бүртгэгдээгүй хамрах хүрээ» гэсэн үг бөгөөд түүнийг 0% гэж тооцно.

Тиймээс **харагдацын томьёог зарласан төсвөөр бодох болгож өөрчилнө** — үүний үр
дүнд харагдацын томьёо `calcProjectProgress`-тэй алгебрийн хувьд яг ижил болж,
системд байсан хоёр rollup **нэг** болно.

`calcProjectProgress` болон `computeProgressFromMap` нь зорилтот томьёо өөрөө тул
**өөрчлөгдөхгүй**.

## 3. Томьёо

| Түвшин | Одоо | Шинэ |
|---|---|---|
| Зураг (task → drawing) | `SUM(t.weight_percent × pct) / NULLIF(SUM(t.weight_percent), 0)` | `SUM(t.weight_percent × pct) / NULLIF(d.weight_percent, 0)` |
| Блок (drawing → block) | `SUM(dp.weight_percent × dp.progress) / NULLIF(SUM(dp.weight_percent), 0)` | `SUM(dp.weight_percent × dp.progress) / 100.0` |
| Баг (block → team) | `SUM(weight_percent × progress) / NULLIF(SUM(weight_percent), 0)` | `SUM(weight_percent × progress) / 100.0` |
| Төсөл (team → project) | `SUM(share_percent × team_prog) / NULLIF(SUM(share_percent), 0)` | `SUM(share_percent × team_prog) / 100.0` |

### Тэнцүү байдлын баталгаа

`calcProjectProgress` = `Σ_b [ b.w × p_b / 100 × share(team(b)) / 100 ]`.

Шинэ томьёогоор `team_prog_t = Σ_{b∈t} (b.w × p_b) / 100` бөгөөд
`project = Σ_t (share_t × team_prog_t) / 100 = Σ_b b.w × p_b / 100 × share / 100`.

Зургийн түвшинд `SUM(t.w × pct) / d.w` нь `calcProjectProgress`-ийн
`SUM(t.w × pct / 100) × 100 / d.w`-тэй ижил.

### ⚠️ JS хувилбарт зургийн жин хаалт болж үлдэнэ

Task-ийн төслийн хувь нэмэр нь `coef = (share/100) × (block.w/100) × (task.w/100)`
болж хялбарчилна — зургийн жин товчлогдоно. **Гэхдээ энэ тэнцэл зөвхөн
`d.weight_percent ≠ 0` үед хүчинтэй.** `calcProjectProgress` нь
`CASE WHEN d.weight_percent > 0 … ELSE 0` салаатай тул 0 төсөвтэй зургийн бүх
даалгавар 0 нэмэрлэдэг.

SQL хувилбарт энэ хаалт `NULLIF(d.weight_percent, 0)`-оос үнэгүй гарна. **JS
хувилбарт гараар бичих ёстой** (`if (drawing.w <= 0) continue`) — хасвал график
SQL-ээс салж зөрнө.

### Захын тохиолдлууд (өөрчлөгдөхгүй)

- `d.weight_percent = 0` → `NULLIF` → NULL → `COALESCE` → 0%. `calcProjectProgress`-ийн
  `ELSE 0` салаатай ижил.
- `blocks.team_id IS NULL` → төслийн толгойд огт орохгүй (0 хувь нэмэрлэнэ).
- Ростерт байгаа боловч блокгүй баг → 0% нэмэрлэнэ, хуваарь нь хуваарилагдсан хэвээр.
- Блок/зураг/баг түвшинд `/ 100.0` тогтмол тул `NULLIF` шаардлагагүй болно.

### 100%-иас давах тухай

Жин 100-аас давсан өгөгдөл дээр шинэ томьёо 100%-иас их тоо гаргаж болно.
**Үүнийг таглахгүй** (`MIN(…, 100)` хийхгүй) — учир нь (1) `calcProjectProgress`
аль хэдийн ингэж ажилладаг тул тагласнаар шинэ зөрүү үүснэ, (2) жингийн алдаа
нуугдахаас илэрсэн нь дээр. Админ жингийн нийлбэрийг тохиргооны хуудсан дээрх
`WeightMeter`-ээс хардаг.

## 5. Хамрах хүрээнээс гадуур (санаатай)

- **Багийн задаргааны жагсаалт** (`routes/projects.ts:188-220`) — зургийн нэрний
  угтвараар бүлэглэсэн жингүй `ROUND(AVG(progress), 2)`. Энэ нь тэс өөр
  зөрүү (бүтцийн `blocks.team_id` ↔ нэрний угтвар гэсэн хоёр өөр багийн зураглал),
  тусад нь авах ёстой.
- **Хугацаа хэтэрсэн төслийн сэрэмжлүүлэг** (`routes/company.ts:622-629`) — блок,
  зураг, багийн жинг огт тоохгүй хавтгай `SUM(t.w × pct/100) / SUM(t.w)`.
  Одоогоор хэвээр үлдээнэ.
- **Жингийн нийлбэрийг сервер талд шаардах** (PUT дээр 400 буцаах) — энэ спекэд
  ороогүй. Харагдац буурснаар админд жингээ засах шахалт өөрөө үүснэ.
- `projects.manual_progress` override — хэвээр, зөвхөн `PROJECT_LIST_SQL` болон
  Timeline дээр үйлчилсэн хэвээр.

## 6. Эрсдэл ба нөлөө

- Энэ нь 2026-07-29-нд оруулсан «бодит жингээр нормчлох» шийдвэрийг **буцаана**.
  Тухайн үед төсөл 37 нь 9.07% → 29.69% болж өссөн; одоо ойролцоогоор 9% руу
  буцна. Төсөл **31/37/39/40/42**-ын хувь мэдэгдэхүйц буурна.
- Авто-архивын 99.999% босго одоо картын тоотой нийцнэ — «карт 100% гэж байхад
  архивлагдахгүй» асуудал арилна.
- Харилцагчийн портал болон PDF тайлан дээрх тоо бас буурна. Хэрэглэгчид энэ
  тухай урьдчилан мэдэгдэх шаардлагатай.
- Timeseries график (төслийн болон компанийн) дээр коэффициентийн нийлбэр 1-ээс
  бага болох тул муруй нь доогуур явна — энэ нь зөв, хүлээгдэж буй үр дүн.

## 7. Шалгах арга

`tsc -b` ба одоо байгаа тестүүд SQL-ийг барихгүй (backend-д зөвхөн 2 тест файл,
хоёулаа цэвэр туслах функц шалгадаг; frontend-д тест байхгүй).

Тиймээс deploy хийхээс өмнө:

1. Production D1 дээр **зөвхөн уншдаг** харьцуулах query ажиллуулна: төсөл бүрээр
   `хуучин хувь`, `шинэ хувь`, `calcProjectProgress` гурвыг зэрэгцүүлж хэвлэнэ.
2. **Хүлээх үр дүн:** `шинэ хувь` ба `calcProjectProgress` бүх төсөл дээр
   бөөрөнхийллийн зөрүүний хүрээнд таарна. Таарахгүй мөр байвал хэрэгжүүлэлт буруу.
3. Үр дүнг хэрэглэгчид харуулж, буурах төслүүдийг баталгаажуулсны дараа л deploy.
4. Deploy дараа: карт дээрх хувь = төслийн дэлгэрэнгүй хуудасны хувь = MCP
   `list_projects`-ийн хувь гэдгийг нэг төсөл дээр гараар шалгана.

Миграци шаардлагагүй — өгөгдөл өөрчлөгдөхгүй, зөвхөн уншилтын томьёо өөрчлөгдөнө.

## 8. Хэрэгжүүлэлтийн дараалал

1. `PROJECT_LIST_SQL` (№1) — эх сурвалж болох томьёо.
2. Үлдсэн 7 хуулбарыг мөр мөрөөр тааруулна (№2-№8).
3. `useProjectTasks.ts`-ийн тайлбар засвар.
4. `CLAUDE.md`-ийн «⚠️ There are TWO rollups and they disagree» хэсгийг шинэчилнэ —
   одоо нэг л rollup байна.
5. Шалгалтын query → хэрэглэгчийн баталгаажуулалт → backend deploy.
