# Ур чадвар / зан чанарын үнэлгээ (Assessments) — техникийн гэрээ

Дотоод судалгаа-тест хөдөлгүүр. Эхний хэрэглээ: **Архитекторуудын ур чадварын
тодорхойлолт** (БА баг). Жилд 1–2 удаа авагдана, дараа нь өөр тестүүд нэмэгдэнэ,
тиймээс бүтэц нь **template-driven** (асуулга DB-д JSON-оор хадгалагдана, кодонд биш).

## 1. Оноолт (эх Excel-ээс задалсан томьёо)

Хэсэг (section) тус бүрд:

| Хэмжигдэхүүн | Томьёо |
| --- | --- |
| `must`    | `мөрийн тоо × scale.max` (жишээ: Concept Design 27 мөр × 5 → 135) |
| `self`    | ажилтны хариултуудын нийлбэр |
| `senior`  | багийн ахлагчийн хариултуудын нийлбэр |
| `average` | **зөвхөн бөглөгдсөн (submitted) талуудын** дундаж. Senior бөглөөгүй бол `average = self` |
| `pct`     | `average / must × 100` |
| `level`   | `pct`-ээс band-аар (зөвхөн `weighted: true` part) |

Зан чанарын (`weighted: false`) part хэсэг бүрд нэмээд **1.0–5.0 дундаж**
(`mean`) тооцогдоно: `mean = average / item_count`. `must = item_count ×
scale.max` тул `must / item_count === scale.max` үргэлж, ө.х. `mean` нь
`pct`-ээс клиент талд шууд гарна (`mean = pct / (100 / scale.max)`, ихэвчлэн
`pct / 20`). `mean` нь `[0, scale.max]`-аас **доош** ч байж болно (хариулаагүй
мөр 0 оноотой тул, жишээ 0.4).

Нийт (зөвхөн `weighted: true` part):
`overallPct = Σ(section.pct × section.weight) / Σ(section.weight)`

### 1b. Багийн (олон хүний) дундаж

`frontend/src/features/assessments/lib/aggregate.ts`. Хүрээ (cohort) нь
**АНХДАГЧААР `'self'`** — өөрийн үнэлгээгээ илгээсэн хүн бүр шууд орно.
Ахлагч нь дараа үнэлээд submit дарвал тухайн хүний `average` шинэчлэгдэж,
багийн дундаж дагаад хөдөлнө (нэмэлт нөхцөл шаардахгүй).

Цуваа бүр **ӨӨРИЙН нэрлэгчтэй**:

| Цуваа | Хэн дээр |
| --- | --- |
| Өөрийн үнэлгээ | self илгээсэн гишүүд |
| Ахлагчийн үнэлгээ | ахлагч үнэлсэн гишүүд (ихэвчлэн цөөн) |
| **Дундаж** | гишүүн бүрийн ӨӨРИЙНХ нь `average` / `pct`-ийн дундаж |

⚠️ Тиймээс «Дундаж» нь self ба senior хоёрын **хооронд байх баталгаагүй** —
senior-той цөөхөн хүн бүх багийг төлөөлөхгүй. Энэ нь буг биш: легендэд цуваа
бүрийн хүний тоог бичиж (`seriesMemberCounts`), `checkAverageInvariant`-ыг
зөвхөн нэрлэгч ижил үед (`hasSharedDenominator`) ажиллуулна. Хатуу
харьцуулалт хэрэгтэй бол админ **«Хоёулаа бөглөсөн»** горим руу шилжинэ —
тэнд бүх гишүүн хоёуланг илгээсэн тул инвариант дахин хүчинтэй.

Энэ дүрэм нь раундын тайлан, зан чанарын radar, хүн тус бүрийн хуудасны
«багийн дундаж» харьцуулалт, Excel export — **бүгдэд** хамаарна (бүгд нэг
`aggregate.ts`-ээс тэжээгддэг).

Level band-ууд (`pct` дээр):

| code | доод | дээд |
| --- | --- | --- |
| `EXPERT` | 95 | 100 |
| `SENIOR` | 85 | 94.99 |
| `MIDDLE` | 60 | 84.99 |
| `JUNIOR` | 30 | 59.99 |
| `INTERN` | 0  | 29.99 |

> `INTERN`-ий доод хязгаар эх файлд 10% гэж бичигдсэн ч бүх мөрд 1 өгвөл 20% гарах
> тул 0-с доош утга практикт үүсэхгүй. Хоосон завсар үлдээхгүйн тулд 0-оос эхэлнэ.

Жин (архитекторын судалгаа, эх Excel-ийн 75%-ийг пропорциональ 100% болгосон):

| # | Хэсэг | Excel | Апп |
| --- | --- | --- | --- |
| 1 | Concept Design | 5% | **7%** |
| 2 | Concept Drawing | 10% | **13%** |
| 3 | Detail Drawing | 30% | **40%** |
| 4 | Project Progress | 5% | **7%** |
| 5 | Project Documentation | 5% | **7%** |
| 6 | Collaborate | 5% | **6%** |
| 7 | Construction Monitoring | 15% | **20%** |
| | **Нийт** | 75% | **100%** |

Жин админ талаас засагдана. Нийлбэр 100 болохгүй бол **шар сэрэмжлүүлэг** (төслийн
`weight_percent`-ийн конвенц) — хадгалахыг хориглохгүй.

Зан чанарын part нь `weighted: false` — `schema.levels`-ээс гардаг `pct`-level,
жин, нийт оноо **байхгүй**. Үүний оронд хэсэг тус бүрийн **1.0–5.0 дундаж**
(`mean`, дээрх томьёо) 5 шатлалын Монгол тайлбартай харагдана:

| code | доод (`minMean`) | дээд (`maxMean`, зөвхөн харуулах) | Тодорхойлолт |
| --- | --- | --- | --- |
| `ILREHGUI` | 1.0 | 1.7 | Илрэхгүй |
| `TOGTVORGUI` | 1.8 | 2.5 | Тогтворгүй |
| `SUURI` | 2.6 | 3.4 | Суурь хангасан |
| `TOGTVORTOI` | 3.5 | 4.2 | Тогтвортой |
| `ULGER_JISHEE` | 4.3 | 5.0 | Үлгэр жишээ |

Band сонголт нь `level`-тэй ижил зарчим: `minMean`-ээр буурахаар эрэмбэлж,
эхний `mean >= band.minMean`-той таарсныг нь авна (дээдээс нь доош хайна) —
тэгвэл 1.75 мэт зайнуудын хоорондох утга, мөн 1.0-ээс доош (хариулаагүй
мөрүүд) утга ч Илрэхгүй band-д унана. Эдгээр band-ууд **схемээс ирдэггүй** —
`frontend/src/features/assessments/lib/behaviorScale.ts` дотор хатуу
кодлогдсон (домэйн үг хэллэг) тул хуучин раундууд ч ШИНЭ band-аар харагдана —
энэ нь `schema.levels`-ийн round-snapshot зарчимаас **санаатай зөрүүтэй**.

Урвуу оноолт **байхгүй** (бүх асуулт шууд нэмэгдэнэ) — `reverse` талбар схемд
байгаа ч архитекторын судалгаанд хаа ч `true` биш.

## 2. Хуудаслалт

`AssessmentSchema.intro` (заавал биш) байвал **хамгийн эхний хуудас** нь
асуултгүй **танилцуулга** болно — Word дээрх «СУДАЛГААНЫ АГУУЛГА» мэт оноо
өгөх мөргүй хэсгүүд энд орно (§8). Тэр хуудас явцын тоололд ордоггүй
(`sections: []` тул `lib/progress.ts` өөрөө 0 гэж тооцно), доод талын товч нь
«Дараах» биш **«Эхлэх»** гэж уриална.

Дараа нь `AssessmentPart.paging`:

- `'section'` — хэсэг тус бүр **тусдаа хуудас**. Ур чадварын part → 7 хуудас.
- `'part'` — бүх хэсэг **нэг хуудсанд**. Зан чанарын part → 1 хуудас.

Архитекторын судалгаа = танилцуулга + **8 хуудас**. Хуудас бүрийн оройд 1–5
онооны тайлбарын legend (sticky; танилцуулга дээр гарахгүй). Хуудас хооронд
шилжихэд **right-to-left slide** (`motion`), хуудас дотор энгийн доошоо scroll.

⚠️ Энэ дүрэм **хоёр газар** хэрэгждэг ба заавал ижил байх ёстой:
`AssessmentFillPage.buildPages` (ажилтны тал) ба
`lib/editorPages.buildEditorPages` (админы засварлагч) — админ засварлагч дээр
харсан хуудаслалт ажилтны талд өөр гарвал редакцийн ажил утгагүй болно.

## 3. Харах эрх

> **2026-08-д өөрчлөгдсөн.** Өмнө нь ажилтан ямар ч хувь/оноо хардаггүй,
> зөвхөн level-ийн нэр/өнгөтэй байсан. Эзний шийдвэрээр ажилтан **өөрийн**
> хувиа хардаг болов — «дараагийн түвшинд хүрэхэд хэдэн хувь дутуу вэ» гэдгийг
> мэдэх нь хөгжлийн ярианы суурь. Хил нь **арилаагүй, нарийссан: зөвхөн өөрийн**.

| Хэн | Юу харна |
| --- | --- |
| Ажилтан (self) | Өөрийн маягт + илгээсний дараа **өөрийн** хувь, түвшин, шатлал дахь байрлал, дараагийн түвшин хүртэлх зөрүү, level-BAND график, мөн **жингээр эрэмбэлсэн сул/хүчтэй 3 хэсэг** (`shortfall = (100 − pct) × weight`). Бусад хүний юу ч харахгүй |
| Багийн ахлагч (senior) | Түүнд оногдсон ажилтнуудын маягт. **Үнэлж буй хүнийхээ бодогдсон хувь/оноог ХАРАХГҮЙ** — senior бол admin биш |
| Admin | Бүх хүний бүх зүйл — тоо, хувь, level, scatter + spider график, Excel export |

### 3a. «Зөвхөн өөрийн» — таван инвариант

`GET /api/assessments/my/results` дээр хэрэгжсэн. Аль нэгийг нь зөрчих
өөрчлөлт нь энэ шийдвэрийн **гадна** — эзнээс дахин зөвшөөрөл ав.

1. **I1** — query-ийн `subject_user_id` нь ҮРГЭЛЖ `user.sub`-т bind хийгдэнэ.
   `?user_id=` / `?subject=` маягийн параметр нэмэхгүй.
2. **I2** — rank / percentile / cohort / «багийн дундаж» талбар нэмэхгүй.
   Эдгээр нь бусдын оноог шууд бус задруулна. Frontend-ийн `benchmark` цуврал
   нь зөвхөн `features/assessments/admin/*`-д дамжина; ажилтны
   `MyResultChartsPage`-д `showBenchmark: false` нь ЖИНХЭНЭ хяналт.
   «Түвшин хэддүгээрт» = **шатлал** дахь байрлал (5 түвшний 3 дахь),
   хүмүүсийн эрэмбэ БИШ.
3. **I3** — `/rounds/*` (бусдын үр дүн) `requireAdmin()` доор хэвээр.
4. **I4** — `senior` ≠ admin. Ахлагч өөрийн бөглөсөн түүхий хариултаа
   `/responses/:id`-ээр хардаг ч үнэлж буй хүнийхээ бодогдсон хувийг хардаггүй.
5. **I5** — зан чанарын (`weighted: false`) хэсэгт **хувь гаргахгүй**. Тэнд
   үнэлгээ нь 1.0–5.0 дундаж (`BEHAVIOR_BANDS`) — өөр системийн хэмжигдэхүүнийг
   хувь мэт харуулбал ажилтан өөрийгөө буруу үнэлнэ. `mean` +
   `nextBandForMean()`-ийн зөрүү л явна.

Хэрэгжилт: `routes/assessments.ts` (`/my/results` mapper),
`lib/assessmentScore.ts` `nextLevelFor()` ↔ frontend `lib/score.ts` (twin),
`lib/behaviorScale.ts` `nextBandForMean()` ↔ frontend twin,
`features/assessments/components/NextLevelHint.tsx` ба
`components/LevelProgressCard.tsx` (сул/хүчтэй 3 хэсэг). Тоог энд ШИНЭЭР
бододоггүй — `scoreAssessment()` аль хэдийн бүгдийг бодсон, өмнө нь mapper
түүнийг хаядаг байсан.

### 3b. «Түвшин ахих зам» — юу дутууг МӨР түвшинд гаргах (2026-08-11)

`backend/src/lib/assessmentGap.ts` → `buildLevelUpPlan(schema, sides)`.
Гарц нь `/my/results`-ийн раунд бүрд ба админы `participantResult`-д
`level_up` талбараар явна (`frontend/.../components/LevelUpPlanCard.tsx`
хоёуланг нь нэг компонентоор зурна).

Өмнө нь ажилтан «Senior түвшинд хүрэхэд 7.7% дутуу» гэсэн ГАНЦ тоо хардаг
байсан — юу хийхийг тэр тоо огт хэлдэггүй. Одоо зөрүү нь **мөрийн жагсаалт**
болж задарна: «Detail Drawing-ийн 24 мөрийг 10–19 төслөөс 20+ төсөл болго =
+2.7%». Мөрийн ард гарах текст нь **схемийн `scale.options[].caption`** —
домэйн үг кодонд hardcode хийгээгүй, асуулга солигдвол текст дагаж солигдоно.

**Хөшүүргийн томьёо** (яагаад мөр бүр өөр үнэтэй вэ):

```
gain = share × 100 × w_s / (must_s × Σw)      // weighted part
share = 1 / (оноонд орсон талын тоо)          // ахлагч илгээсэн бол 0.5
```

Архитекторын асуулгад энэ нь дараах зөрүү гаргана — **төлөвлөгөө нь хувиар
БИШ, хөшүүргээр** эрэмбэлэгдэх болсон шалтгаан:

| Хэсэг | Жин | Мөр | +1 мөр = |
| --- | --- | --- | --- |
| Detail Drawing | 40% | 36 | **0.2222 pp** |
| Construction Monitoring | 20% | 53 | 0.0755 pp |
| Concept Drawing | 13% | 35 | 0.0743 pp |
| Project Progress / Documentation | 7% | 26 | 0.0538 pp |
| Concept Design | 7% | 27 | 0.0519 pp |
| Collaborate | 6% | 40 | **0.0300 pp** |

Detail Drawing-ийн нэг мөр Collaborate-ийнхаас **7.4 дахин** үнэтэй. Хүн
«хамгийн сул хэсгээ» засаад нийт хувь нь бараг хөдөлдөггүйн шалтгаан энэ —
`weakest[3]` нь хэсгийн түвшинд зөв эрэмбэлдэг ч юу хийхийг хэлдэггүй байв.

Тогтмол дүрмүүд:

- **Дээд түвшинд `next_level = null`, `steps = []`, `at_top_level = true`.**
  «0% дутуу» гэж ХЭЗЭЭ Ч харуулахгүй — тэнд зөрүү гэдэг утгагүй.
  Зан чанарын хэсэгт мөн адил (`BEHAVIOR_BANDS`-ийн `ULGER_JISHEE`).
- Зан чанарт `unit: 'mean'` — хувь гаргахгүй (I5). Ур чадварт `unit: 'pct'`.
- **`answerScore` нь `itemScore`-ыг ӨӨРӨӨ дуудна** — ө.х. `item.reverse`-ийг
  `sumSection`-той яг адил урвуулна. Хуулбарлаж бичвэл `current` нь
  `scoreAssessment`-ийн `pct`-ээс салж, урвуу мөрийг ЭСРЭГ чиглэлд түлхэнэ.
  Гарцад харуулах `from`/`to` нь ОНОО биш, **маягтын шатлалын утга**
  (`rawOfScore`) — учир нь `caption` нь сонголтыг тодорхойлдог. Урвуу мөрд
  `to.value < from.value` байх нь ХЭВИЙН.
- Шуналт сонголтын эрэмбэ `(gain ↓, toScore ↑)`. Нэг мөрийн алхмуудын gain
  хэзээ ч өсдөггүй (эхний «хариулаагүй → `scale.min`» алхам нь `scale.min`
  оноо ахиулдаг тул хамгийн том) тул `k`-р алхам нь `k−1`-ийн ДАРАА л
  сонгогдоно — урьдчилсан нөхцөл эрэмбэнд шингэсэн.
- **`groupSteps` нь ЭХЛЭЭД мөрөөр нэгтгэнэ.** Нэг мөрд хоёр алхам сонгогдвол
  (3 → 4 → 5) тэр мөрийн ЭЦСИЙН зорилтыг («3 → 5») харуулна. Алхам бүрийг
  тусад нь бүлэглэвэл ижил 9 мөр «3→4» ба «3→5» гэсэн хоёр зөвлөмжид
  давхардан гарна.
- `from.value === 0` = **хариулаагүй мөр** (шатлалд байхгүй утга, `label`/
  `caption` нь null). 0 → `scale.min` алхам нь `scale.min` ОНОО ахиулдаг тул
  gain нь бусад алхмаас их (шатлал 1-ээс эхлэхгүй схемд мэдэгдэхүйц).
- **Хөшүүргийн хуваарь нь `usedWeight`** — ө.х. `overall.current`-ийн ЯГ ижил
  хуваарь (зөвхөн хувь нь бодогдсон хэсгүүдийн жин). Жинтэй атлаа асуултгүй
  хэсэг (`validateSchema` `groups: []`-г зөвшөөрдөг) байхад бүх жингээр
  хуваавал ашиг дутуу тооцогдож илүү алхам тушаана.
- **`roundPct`.** `/my/results` нь бүх хувиа `shownBands()`-аар (эхлээд `pct1`,
  дараа нь band) гаргадаг тул тэр route `roundPct: pct1`-ийг ЗААВАЛ
  дамжуулна — эс бөгөөс band-ын ирмэгийн 0.05-ийн цонхонд нэг хариултын
  дотор ХОЁР өөр түвшин зэрэг гарна (түүхий 84.96 → «85.0% Senior» ба
  «Middle, Senior хүртэл 0.0%»). Админы `participantResult` нь ТҮҮХИЙ хувь
  буцаадаг тул `roundPct` дамжуулахгүй.
- `covered = false` бол ажилтан ӨӨРИЙН бүх хариултаа дээд оноо болгосон ч
  энэ раундад дараагийн түвшинд хүрэхгүй (ахлагчийн оноо хагасыг эзэлдэг).
  UI үүнийг ЧИМЭЭГҮЙ өнгөрөхгүй — эс бөгөөс жагсаалт «үүнийг хийвэл болно»
  гэж худал уншигдана. ⚠️ Сэрэмжлүүлэг нь `steps.length > 0` салаанаас
  **ГАДНА** байна: `covered = false`-ийн хамгийн цэвэр тохиолдол нь яг
  `steps === []` (ахиулах мөр үлдээгүй) юм.
- **`level_up` нь жагсаалтын гарцад ОРОХГҮЙ.** `/rounds/:id/results` нь
  оролцогч бүрийнхийг цувуулбал 30 хүнтэй раундад хариулт 3.6–5.2 дахин
  томордог ба ямар ч дэлгэц түүнийг уншдаггүй. `participantResult`-ийн
  `includeLevelUp` нь зөвхөн `/rounds/:id/results/:userId`-д true; админы
  хуудас түүнийг тусад нь татна (`fetchParticipantResult`).
- **I1–I5 зөрчихгүй**: бүх тоо нь тухайн ажилтны өөрийн хариулт + схемийн
  жин/шатлал + аль хэдийн буцаадаг `pct` гурваас гарна. Өөр хүний ямар ч
  утга ОРООГҮЙ. `covered`/`total_gain` нь ажилтанд ч явна (шинэ задралт
  БИШ — өөрийн өгөгдлөөс бодогдоно), гэхдээ ШИНЭ тоон талбар нэмэхийн өмнө
  I2/I4-ийг унш.
- **Түүхий hex-ийг `ui/badge`-ийн дүүргэлт болгож болохгүй** —
  `variant="default"` нь `text-primary-foreground`-оо хадгалдаг тул текст нь
  сэдвээс, дэвсгэр нь схемээс гарч контраст унана (харанхуй сэдэвт
  «Суурь хангасан» `#e8dfa6` дээр цагаан текст = 1.35:1). Канон зам нь
  `LevelBadge` — өнгө/дэвсгэр/хүрээг alpha-аар хамт барина.
- **Клиент дээр twin БАЙХГҮЙ** — тооцоол зөвхөн серверт. `score.ts` шиг
  хоёр талд давхардуулбал хөшүүргийн томьёо чимээгүйхэн салж, ажилтан
  админаас өөр зөвлөмж хардаг болно. Тест: `backend/src/lib/assessmentGap.test.ts`
  (16 тест, архитекторынхоос ӨӨР синтетик схем дээр — hardcode эсэхийг
  зөвхөн ингэж барина; `reverse`, асуултгүй хэсэг, `roundPct`, мөрийн
  нэгтгэлийг тусад нь барина).

**Мэдэгдэж буй хязгаар — өөрөө мэдүүлсэн туршлага.** `scale.options`-ийн
тайлбар нь «20 ба түүнээс дээш **төсөлд**…» гэж бодит төслийн тоог заадаг ч
энэ тоог систем **хаана ч шалгадаггүй**: `routes/assessments.ts` дотор
`projects` / `tasks` / `progress_entries` рүү заасан ганц ч query байхгүй.
Тиймээс «энэ хүн 15 төсөлд ажилласан, 5 нь дутуу» гэж ЯГ хэлэх боломжгүй —
одоогийн хөдөлгүүр «4 → 5 болгох = 20+ төсөлд гүйцэтгэсэн байх» гэсэн
**мужаар** л ярина. Бодит тоо руу холбохын тулд ажилтан ↔ төслийн оролцооны
хэмжүүр (`progress_entries` / `tasks.assigned_to` / `project_team_shares`)
хэрэгтэй — тэр нь тусдаа шийдвэр.

> **I4-ийн хязгаар — талбар буцаахгүй ≠ мэдээлэл нуугдана** (2026-08-10,
> review-ээр илэрсэн; ЗОРИУДААР хүлээн зөвшөөрсөн). Ахлагч илгээсний дараа
> `pct = (self + senior) / 2`. Ажилтан өөрийн хариултаа `/responses/:id`-ээр
> уншиж `self_pct`-ээ бодож чадах тул `senior_pct = 2 × pct − self_pct` гэж
> СЭРГЭЭГДЭНЭ. Өөрөөр хэлбэл I4 нь энэ дэглэмд математикаар баталгаажихгүй —
> жинхэнэ хаах цорын ганц зам бол жигнэсэн хувийг огт буцаахгүй байх, тэр нь
> 2026-08-ны шийдвэрийг буцаана. Шинэ тоон талбар нэмэхийн өмнө үүнийг унш.

**Бөөрөнхийлөлт.** `/my/results`-ийн бүх хувь `shownBands()`-аар дамжина:
ЭХЛЭЭД 1 аравтын орон хүртэл бөөрөнхийлж, ДАРАА нь band-д хуваарилна.
Түүхий хувиас band-ыг, бөөрөнхийлсөнөөс зөрүүг бодвол band-ын ирмэгийн
0.05-ийн цонхонд карт өөртэйгөө зөрчилдөнө (түүхий 84.96 → «85.0%, Middle,
Senior хүртэл 0.0%» атлаа шатлал дээр Senior аль хэдийн асчихсан).

## 4. Өгөгдлийн загвар (migration 0139 · 0142 · 0146)

```
assessment_templates(id, code UNIQUE, title_mn, title_en, description,
                     schema_json, status draft|active|archived,
                     team_codes,          -- 0146: JSON массив текст '["BB"]'
                     senior_user_ids,     -- 0147: анхдагч үнэлэгчид '[3,4]'
                     created_by_id, created_at, updated_at)

assessment_rounds(id, template_id, name, period, status draft|open|closed,
                  schema_json,  -- template-ийн SNAPSHOT (round эхэлсний дараа
                                -- template засагдсан ч энэ round өөрчлөгдөхгүй)
                  opens_at, closes_at,
                  team_codes,      -- 0146: раунд ямар багт явсан
                  senior_user_ids, -- 0146: JSON массив '[3,4]' — раунд ДАЯАР
                                   --       үнэлэх senior-ууд
                  created_by_id, created_at, updated_at)

assessment_participants(id, round_id, user_id, evaluator_user_id,
                        UNIQUE(round_id, user_id))

assessment_responses(id, round_id, subject_user_id, evaluator_user_id,
                     evaluator_kind self|senior, answers_json,
                     status draft|submitted, submitted_at,
                     created_at, updated_at,
                     -- 0142: evaluator_user_id нь түлхүүрт ОРСОН тул нэг
                     -- ажилтанд олон 'senior' мөр зэрэгцэн оршино
                     UNIQUE(round_id, subject_user_id, evaluator_kind,
                            evaluator_user_id))
```

`answers_json` = `{ "<itemId>": 1..5 }` — хавтгай map, item id нь схемийнхтэй тохирно.

**Үнэлэгч оноох хоёр горим** (`POST /rounds`, `PUT /rounds/:id/participants`):

- `senior_user_ids` илгээвэл — сонгосон senior бүр **бүх** оролцогчийг үнэлнэ
  (өөрийгөө үнэлэхээс бусад), өөрөөр хэлбэл `оролцогч × senior` бүрд нэг
  `senior` мөр үүснэ. Зөвхөн идэвхтэй `role='senior'` хэрэглэгч зөвшөөрөгдөнө.
  `assessment_participants.evaluator_user_id` нь эхний senior-ийг л барина
  (хүснэгтийн нэг баганад зориулсан төлөөлөл) — жинхэнэ бүрэн жагсаалт нь
  `assessment_responses`-д.
- илгээгээгүй бол хуучин зам: хүн тус бүрийн үндсэн багийн `teams.lead_user_id`.

⚠️ `senior` маягтыг оролцогчийн жагсаалтад **LEFT JOIN-оор** татаж болохгүй —
олон ахлагчтай үед оролцогч давхардана. `fetchParticipants` нь корреляц дэд
query-ээр `senior_total` / `senior_submitted` болгож нэгтгэдэг; `senior_status`
нь **бүгд** илгээсэн үед л `'submitted'` болно.

## 7. Frontend байршил

- Profile-ийн шинэ таб «Ур чадварын үнэлгээ» — «Хөгжлийн төлөвлөгөө» табын **баруун талд**.
- `/app/assessments/:responseId` — бөглөх wizard (AppShell дотор).
- `/app/assessments/results/:roundId` — ажилтны өөрийн level-band график (илгээсний дараа; 2026-08-аас ӨӨРИЙН хувь + дараагийн шатлал хүртэлх зөрүү харагдана, §3).
- `/app/admin/assessments` — админы **жагсаалт** + үр дүн (admin-only, sidebar-ийн Админ бүлэгт).
- `/app/admin/assessments/templates/:templateId` — асуулгын **бүтэн дэлгэцийн засварлагч**
  (`TemplateEditorPage`). Layout-ийн `isFullBleed` угтвараар бүтэн талбайг эзэлнэ.

Графикууд (`recharts`, аль аль нь репод шинэ):

- Ур чадвар → **connected scatterplot** (`ScatterChart` + `Scatter line`), X = 7 хэсэг, Y = level slot (`pct`-ээс `levelForPct`-аар).
- Зан чанар → **spider / radar** (`RadarChart`) + connected scatterplot хос (`BehaviorPartDualCharts`), тэнхлэг = зан чанарын хэсгүүд, Y/радиус = **1.0–5.0 дундаж** (`valueMode="mean"`, `levelChartAxis`-ийн level-slot логикийг ашиглахгүй — шууд тоон тэнхлэг, тик нь band-уудын `minMean` дээр). Band босгуудыг зурагт цагирга/туузаар тэмдэглэнэ.
- Өнгө: `self` = хөх, `senior` = улбар шар, `average` = ногоон. Багийн харагдац = гишүүдийн дундаж нэг шугам.

Excel export (`exceljs`, lazy): REPORT DIAGRAMM хүснэгт + асуулт бүрийн хариулт +
2 график **PNG зураг** болж (SVG → canvas → PNG → `workbook.addImage`).

## 8. Word (.docx) import ба бүтэн дэлгэцийн засварлагч

Админ `.docx` чирж оруулна → `fflate`-ээр `word/document.xml` задалж, DOMParser-оор
догол мөр бүрийг текст + `w:numPr` (ilvl/numId) хамт уншина → эвристик ангилагч:

| Хэв маяг | Тайлал |
| --- | --- |
| `N. ТОМ ҮСГЭЭР ГАРЧИГ` эсвэл `N.N НЭР` | section |
| `N.N.N Текст` | group (дэд асуулт) |
| `N. Текст` эсвэл жагсаалтын элемент | item (1–5 оноо өгөх мөр) |
| Хаалтанд авсан `(…)` догол | тухайн section/group-ийн тайлбар |

**Оноо өгөх мөргүй (0 мөртэй) хэсгүүд хог БИШ** — `paragraphsToDraft` тэднийг
хоёр янзаар ялгана:

- асуулттай хэсгийн **яг өмнө** зогсож буй нь → тухайн part-ын **гарчиг**
  («ТУРШЛАГА ДЭЭР ҮНДЭСЛЭСЭН УР ЧАДВАРЫН АСУУЛГА», «ЗАН ЧАНАРЫН АСУУЛГА»),
- бусад нь → **танилцуулга блок** (`schema.intro`, §2) — ажилтан бөглөхийн
  өмнө уншина.

Ийм зааг **хоёр ба түүнээс олон** байвал `paragraphsToDraft` нь `split`
**САНАЛ** буцаана (Word дээр 2 судалгаа нийлсэн). Салгалт **хэзээ ч автоматаар
хэрэгжихгүй** — засварлагч дээр `SplitPartsPrompt` гарч админ зөвшөөрнө.
Зөвшөөрвөл `applyPartSplit` нь «зан чанар» гэсэн гарчигтай part-д `behavior`
шатлал + radar + `weighted:false` + `paging:'part'`-ыг анхдагчаар өгнө.
Саналыг **индексээр** (key-ээр БИШ) илэрхийлдэг — санал сервер рүү нэг эргэж
ирдэг ба тэр үед ноорогийн бүх түр key шинээр үүсдэг.

Таних нь төгс байх боломжгүй тул **заавал засварлах алхам** гарна. «Үргэлжлүүлэх»
дарахад сервер дээр `status='draft'` template үүсч (`createDraftTemplate`,
код мөргөлдвөл `-2`, `-3`… залгана) `/app/admin/assessments/templates/:id` руу
шилжинэ — санах ойд үлдээвэл tab хаагдахад 206 мөр алга болно.

**Засварлагч (`TemplateEditorPage`) — гурван багана:**

| Багана | Юу |
| --- | --- |
| зүүн | хуудасны жагсаалт — ажилтны харах дараалалтай ЯГ ижил (`buildEditorPages`) |
| гол | засагддаг «ажилтны хуудас» (`EditablePage`) — текст дээр дарж засна, hover дээр ↑↓/+/🗑 |
| баруун | тоон/бүтцийн тохиргоо — жин, код, шатлал, график, хуудаслалт, **баг**, **үнэлэгч (senior)** |

Баг ба үнэлэгч хоёулаа **загварт** хадгалагдана (`team_codes` 0146,
`senior_user_ids` 0147) — эдгээр нь зөвхөн АНХДАГЧ санал: «Багтаа илгээх»
диалог тэднийг урьдчилан тэмдэглээд ирэх бөгөөд админ тэндээ өөрчилж болно.
Жинхэнэ оноолт нь раунд дээр (`assessment_rounds.senior_user_ids`) бичигдэнэ.
Загварт үнэлэгч сонгоогүй бол диалог нь сонгосон багийн `lead_user_id`-г
санал болгоно.

Голын текстүүд нь тунгалаг `<textarea>` (`EditableText`) — `contentEditable`
БИШ: сүүлийнх нь кирилл/IME оруулга дээр re-render бүрт курсор алддаг.
Оноо өгөх 1..5 товчнууд харагдана ч **идэвхгүй** (админ хариулт өгөхгүй).

Хадгалалт нь **autosave** (2.5с debounce, `useTemplateAutosave` — `PUT
/templates/:id`). Код/монгол нэр хоосон бол сервер 400 буцаах тул хүсэлт
илгээхгүй, оронд нь толгойд шар сэрэмжлүүлэг гарна.

**Сүүлчийн алхам — «Багтаа илгээх»** (`PublishDialog`): раундын нэр/период,
оролцогчид (баг эсвэл role; баг нь template-ийн `team_codes`-оос урьдчилан
бөглөгдөнө), раунд даяарх senior-ууд (зөвхөн `role='senior'`; сонгосон багийн
`lead_user_id` автоматаар тэмдэглэгдэнэ), «одоо нээх үү». Илгээхийн ӨМНӨ
autosave-ийг `flush()`-аар дуустал хүлээнэ — эс бөгөөс раунд ХУУЧИН схемийн
snapshot авна. Мэдэгдэл (`assessment_assigned`) нь апп дотор + `pushSweep`-ээр
web push болж явна.

Админы `/app/admin/assessments` хуудсанд асуулга ЗОХИОХ/ЯВУУЛАХ UI байхгүй —
«Шинэ загвар» нь хоосон ноорог үүсгээд засварлагч руу, «Шинэ судалгаа» нь
загвар сонгуулаад `?publish=1`-тэйгээр мөн засварлагч руу чиглүүлнэ.
